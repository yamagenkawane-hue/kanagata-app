# 金型生産管理システム：最新仕様と実装状況

更新日：2026-10-02（日本時間）。本書を現在の仕様・操作・状態の入口とする。以前の文書は作成時点の履歴として保存する。
コード確認対象：mainの4e5e359までの実装。文書整理自体はその後のコミットに含まれる。

## 1. 対象と構成

PCで約10名が利用する金型生産管理システム。Next.js 16・React 19・TypeScript strict・Supabaseを使用する。製品1件を金型1件として扱い、別の管理番号・金型名を入力しない。
DB業務画面は`/workspace`、ログインは`/login`、初期管理者登録は`/setup`、確認用デモは`/demo`。
DB画面はSupabaseから取得・保存し、デモだけがメモリ内の架空データで再読み込み時に戻る。

## 2. ログイン・ユーザー設定

- ログイン画面の入力はユーザーID・パスワード。メールアドレスは不要。
- IDは3〜32文字の半角英数字・ハイフン・アンダースコア。先頭は英数字。数字だけの社員番号も使用可能。
- 大文字・小文字は区別せず小文字へ正規化する。
- 新規登録パスワードは8〜128文字。確認用入力との一致を確認する。Supabase側に追加条件があればその条件も適用される。
- 初期管理者登録は表示名・ID・パスワード・確認用パスワード。合言葉は不要。
- プロフィールが1件でも存在すると初期登録を閉鎖する。SQLの行ロックで同時初期登録も制限する。
- 追加ユーザーは管理者がユーザー設定の「利用者を登録」から登録する。UUID手入力は不要。
- 既存利用者の表示名・管理者／担当者・利用可否を編集できる。最後の有効な管理者を降格・停止できない。
- IDをサーバー内部で`ID@users.kanagata.invalid`へ変換しSupabase Authで認証する。これは配送用メールではなく、登録時のメール送信は行わない。パスワードを業務テーブルへ保存しない。
- メール方式で登録された旧アカウントがある場合、ID方式への個別移行が必要。既存アカウントを自動削除・変更しない。

## 3. 権限

| 操作 | 管理者 | 担当者 |
| --- | --- | --- |
| 予定追加・変更・加工順変更・日程確定 | 可 | 不可 |
| 自分・他の担当者の実績入力・修正 | 可 | 可 |
| 実績削除 | 可 | 不可 |
| 金型・BOM・工程管理・カレンダー変更 | 可 | 不可 |
| 利用者作成・権限変更 | 可 | 不可 |

実績削除は論理削除・監査ログ。金型・BOM・製作ロットは非表示、機械は使用停止で履歴を残す。作業中・完了済みロットは取消できない。未完了予定のある設備は停止できない。

## 4. 金型・BOM

金型の登録項目は製品名・取引先・納期・備考。製品名・納期は必須。
BOM登録・編集は区分→名称の順。続いて金型・必要数量・必要工程・備考を設定する。図番は不要。パーツ名は自由入力、プレート名は次の10種類から選ぶ。

| コード | 名称 |
| --- | --- |
| PP | PPパンチプレート |
| PB | PBパンチバッキング |
| SP | SPストリッパープレート |
| SB | SBストリッパーバッキング |
| DP | DPダイプレート |
| DB1 | DB1ダイバッキング |
| DB2 | DB2ダイバッキング |
| DB3 | DB3ダイバッキング |
| DS1 | DS1ダイセット |
| DS2 | DS2ダイセット |

同じ金型で有効な登録済みプレートは新規選択肢から除外する。非表示になった名称は再登録できる。編集時は現在の名称を残し、他の行で使用中の別プレートへの変更は拒否する。既存の重複した2行はいずれも編集でき、未使用プレートへ変更できる。旧自由入力名は変更せず保持できる。
プレートは全5工程、パーツは必要工程を選択する。BOMの所属金型は登録後変更不可。
BOM変更で過去実績や登録済み製作ロット名を自動改名しない。変更後に追加するロットが変更後のBOM名称を使用する。

## 5. ガントへの登録と数量

「BOMから予定を追加」で金型→BOM項目→今回製作数量を選び、必要工程ごとの機械・担当者・所要時間・開始条件を設定する。1件ずつ登録し、必要数量内で複数ロットに分割できる。
必要数量／登録済み／未登録数量を表示し、合計がBOM必要数量を超える追加製作を拒否する。未着手ロットの取消で数量枠が戻る。登録済みロットの数量は直接変更せず、未着手の場合は取消・再登録する。BOM必要数量は登録済み数量未満に減らせない。

## 6. 工程・機械・画面遷移

標準順はマシニング→自動研磨→ワイヤー→型組→トライ。プレートは全部、パーツは選択した工程だけをこの順で実施する。繰り返し・任意順序変更は対象外。
管理画面の名称は「工程管理」、ボタンは「＋ 工程を登録」。現在の機能は標準5工程に属する機械の登録・編集・停止であり、任意の第6工程などを新設する機能ではない。
ワイヤーはデモ・テストデータで4台を用意する。実際の機械名・その他の台数は運用時に登録する。

| 画面 | URL | 主な内容 |
| --- | --- | --- |
| 生産計画 | `/workspace` | 金型別ガント、プレート・パーツ名のバー、1・3・7日表示、30分目盛り、検索、加工順、追加・編集・再計算 |
| 金型管理・詳細 | `/workspace/products`、`/workspace/products/{id}` | 金型登録・編集・非表示、BOM導線、製作ロット |
| BOM設定 | `/workspace/bom` | 必要項目・数量・必要工程、登録・編集・非表示 |
| 工程詳細 | `/workspace/process/{code}` | 指定工程の金型別ガント |
| 機械詳細 | `/workspace/machines/{id}` | 指定機械の加工予定・加工順 |
| 工程管理 | `/workspace/equipment` | 標準工程ごとの機械登録・編集・停止 |
| ユーザー設定 | `/workspace/users` | ログインユーザー登録、表示名・役割・有効状態 |
| 会社カレンダー | `/workspace/calendar` | 稼働日・休日、Excel取込、日別変更 |
| 作業実績 | `/workspace/actuals` | 実績一覧、記録時間・日別自動計算・修正理由・削除 |

工程名・機械名・金型名から関連詳細へ遷移する。実績編集はガントから行う。

## 7. 日程計算

所要時間は30分単位、開始・終了は1分単位。未着手の加工順を機械ごとに1・2・3…と指定し、飛び込み挿入で後順位を振り直す。金型の工程順とは別の順位。
開始条件・前工程の終了・所要時間・設備の空き・会社カレンダーを使って後工程を自動計算する。重複は空き時間へずらす。管理者は重複警告を確認して手動の重複配置も保存可能。
自動調整は未着手かつ非固定だけ。作業中・完了済み・固定予定を維持する。変更前後と納期超過を確認してから管理者が確定する。
勤務時間8:50〜17:40、昼休み12:00〜12:50、休憩15:00〜15:10、実働470分。通常は勤務時間・稼働日内。マシニング・自動研磨・ワイヤーはタスクごとに夜間指定でき、指定時は休憩・夜間・休日を継続できる。休憩中稼働も設定可能。

## 8. 実績・カレンダー

状態は未着手・作業中・完了。進捗率は入力しない。作業者・開始・終了を入力し、休憩を除いた作業時間を自動計算する。修正時間・任意の理由も保存可能。日別の表示は自動計算値で、修正した総時間を日別へ自動配分しない。
担当者も他者の実績を入力・修正できる。重複実績は確認して保存可能。実際の時刻は移動しない。実績保存後の予定再計算は管理者が別に確認・確定する。過去実績の休憩設定は保存時の内容を保持する。
会社カレンダーは全日設定。Excel手動取込であり定期自動取込はない。標準xlsxの先頭シートに「日付」「稼働日」を配置、稼働日は1／0または稼働／休日。2000日以内・ファイル1MB以内。プレビューを確認して保存する。同じ日付を上書きし、重複日付・不正値は拒否する。

## 9. DB設定・起動手順（現行）

Node.js24。`npm ci`の後、`.env.local`を設定する。接続URL・Publishable keyに加え、アプリで利用者を作成するためのサーバー専用Secret keyが必要。

```dotenv
NEXT_PUBLIC_SUPABASE_URL=プロジェクトURL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=Publishable_key
SUPABASE_SECRET_KEY=サーバー専用Secret_key
```

Secret keyにNEXT_PUBLIC接頭辞を付けない。従来のservice_roleキーはSUPABASE_SERVICE_ROLE_KEYでも対応。INITIAL_ADMIN_SETUP_TOKENは未使用・不要。環境変数・実接続キーはGitに含めない。
新規DBだけ、SQL Editorで以下を順番に1回実行する。適用済みSQLを再実行しない。

1. `supabase/migrations/202609300001_initial_schema.sql`
2. `supabase/migrations/202610010001_bom_and_mutations.sql`
3. `supabase/migrations/202610010002_login_users.sql`

`npm run dev`で起動し、`http://localhost:3000/setup`で最初の管理者を登録、`/login`でログインする。追加ユーザーはユーザー設定から作成する。環境変更後は再起動する。本番は`npm run build`の後`npm run start`。
テストデータは管理画面の「初期セットアップ・テストデータ」から登録する。金型2件・BOM4項目・設備10台（ワイヤー4台）・約180日の架空カレンダー・プレートロット2件・予定10工程を追加。既存データは消さず、既存カレンダー日は上書きしない。同じシードの再登録は拒否する。

## 10. 保存・検証・確認状態

認証・役割・入力形式・Origin・入力サイズをAPIで確認し、業務更新RPCは役割とrevisionを再確認する。数量上限・更新競合・監査ログをトランザクションで処理する。利用者登録RPCはサーバー専用ロールだけに許可し、DB保存失敗時はその要求で新規作成したAuthアカウントのみ取消を試みる。
プレート名称・同一金型の重複選択制限は画面とAPIで検証する。DBのmanage_entityを直接呼ぶ場合の新プレート制限は未追加。
