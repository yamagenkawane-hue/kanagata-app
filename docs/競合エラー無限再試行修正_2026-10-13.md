# 競合エラーによるPostgREST内部再試行の修正

API Gatewayは直近60分16件、Postgresは約35.8万件というユーザー画像を確認。外部から毎秒907要求が来ているとは判断できない。前の調査で示した失敗要求の繰返しには、PostgREST内部の再試行も含まれる。

Supabase公式の既知問題は、RPCで業務上の競合にSQLSTATE `40001` を使用するとPostgREST 14が無限再試行するもの。ユーザー環境はPostgREST 14.18。実装の `app_private.lock_revision` と利用者登録RPCは、リビジョン競合時にこのコードを返していた。少数のHTTP要求、同時に繰返されるcommit_plan、成功監査が増えない、大量の設定SQLという症状と一致する。実DBログの40001確認・適用後の収束確認は未完了なので、主因の確定は適用後の観測で行う。

`202610130002_conflict_no_retry.sql` は競合コードを `PT409` に変更する。これはPostgRESTがHTTP409として返し、40001の再試行対象にならない。認証、行ロック、監査、業務データは維持する。利用者登録RPCがある場合も同じ修正を適用する。API側はPT409を409として扱い、旧SQL環境との互換のため40001も既存マッピングを維持する。

SQL Editorで追加SQLを実行する。接続強制終了やデータ削除、権限緩和は不要。適用後にCPUと設定SQLのcalls増加、Postgresログを確認する。

PGliteで競合時のPT409、成功保存、失敗時のデータ・リビジョン保持、管理者チェック、未認証拒否、利用者登録の競合を検証した。実PostgREST経由での再試行停止はDB適用後に確認が必要。

公式資料：https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b
