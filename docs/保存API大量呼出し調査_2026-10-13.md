# 保存APIの大量呼出し調査（取得最適化後）

## 確認できた事実
ユーザー提供の実DB統計で、設定SQLの呼出回数が2026-10-13 09:44:37.072373 UTCの471735102回から、09:44:51.240861 UTCの471747952回へ増えた。差分は14.168488秒で12850回（毎秒約907回）。実行時間差分は372.8ms。このSQLだけからCPU占有率を計算したり、CPU100%の主因と断定したりはしない。

ユーザーは測定時に生産管理システムを開いていないと回答。接続の詳細ではPostgRESTの5接続が `public.commit_plan` を同時実行または直前に実行し、うち1接続は `idle in transaction (aborted)` だった。全接続の `blocking_pids` は空。負の数十msの継続時間は、`now()` が調査トランザクションの開始時刻を返し、活動の時刻がその後に更新された場合にも起きるため、長時間滞留や時計異常の証拠ではない。

13日間idleの `LISTEN "pgrst"` は通知待ち接続であり、それだけで不具合とはしない。

実DBを読み取り専用で確認：revision=52、needs_recalculation=true。最新の成功監査は10月8日の設備変更。最新の予定保存は10月8日10:43:04 UTC。大量呼出しが観測された10月13日の成功監査は直近記録にはなかった。

リポジトリ内の保存経路を確認：`commit_plan` は明示的な日程確定操作から呼び出す。保存APIの自動再試行・定期呼出しはソースに見つからない。ローカルプロセスのコマンド本文や認証情報を表示せず種類を確認したが、発生元を特定する証拠は得られなかった。
